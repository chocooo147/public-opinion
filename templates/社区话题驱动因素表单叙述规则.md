# 社区话题驱动因素表单叙述规则

> Rule version: `editorial-calibration-v1-2026-08-18`

## 1. 规则目的

本规则用于指导社区舆情分析人员或自动化模型，将一周内分散的玩家讨论整理为表单中的话题级摘要。

目标是让每一条内容清晰回答：

1. 玩家在讨论什么；
2. 玩家对该话题持什么态度；
3. 该态度由什么具体因素形成；
4. 该讨论是否影响体验、期待、信任、参与或消费行为。

---

## 2. 表单结构锁定原则

本规则不得改变现有表单结构。

从 W30 起，结构锁定为**单工作表左右中英对照**：英文位于左侧，中文位于右侧，同一驱动因素必须在同一行组中一一对应。不得输出中英文分离工作表，不得恢复为多页摘要、数据明细和质检分表。

现有结构保持为：

| 层级 | 当前字段 / 内容 | 功能 |
|---|---|---|
| 区域层 | CHINA | 界定分析市场 |
| 数据层 | Weekly Conversations | 说明本周社区讨论规模 |
| 数据层 | Engagements | 说明本周互动热度 |
| 话题层 | TOPIC / DRIVER | 概括社区讨论对象 |
| 判断层 | Positive / Neutral / Negative / Mixed | 标记话题情绪方向 |
| 解释层 | Narrative / Summary | 默认用2—3句紧凑文字解释玩家反应、原因与影响；硬长度以当前合同为准 |

不得新增、删除或调整表单中的现有字段。

允许补强的内容仅包括：

- 字段填写规则；
- 话题选择逻辑；
- 叙述顺序；
- 用词标准；
- 情绪判断标准；
- 数据质量检查；
- 自动化生成约束。

---

## 3. 表单整体写作逻辑

表单的核心叙述链路为：

> 话题对象 → 玩家反应 → 具体原因 → 比较或转折 → 结果影响

表单采用：

> 标签负责给出结论，正文负责解释结论。

因此正文不应机械重复 Positive、Neutral、Negative 或 Mixed，而应说明为什么形成该情绪判断。

---

## 4. 话题形成与排序规则

### 4.0 本周事件 / Issue 前置层

Weekly Report Driver 不得直接由 canonical Data Topic 生成。

生成 Driver 前，必须先根据当周真实 evidence 建立完整的 **Current-week Event / Issue inventory**，识别玩家本周实际讨论的具体对象、版本变化或事件，例如：

- 英雄重做；
- 武器平衡调整；
- 弹药机制改动；
- 战利品系统变化；
- 皮肤、传家宝或礼包；
- 赛事与中国队伍表现；
- 技术问题。

该层属于 `evidence_and_editorial_synthesis` 内部的编辑归纳步骤，不新增表单可见字段，不创建新的 canonical Topic，也不得改写冻结 Topic 注册表。

### 4.1 Editorial Selection Ladder

所有 Event / Issue 在进入最终 Driver 竞争前，先按定性优先级分为 A / B / C / D。该分层不是数值 Impact Score，不得自行创建权重公式或硬阈值。

#### Band A — Must Compete

本周明确的版本改动、产品、模式、机制、英雄/武器重做、商业化对象，以及具有实质玩家反应的命名赛事/中国队伍表现。

所有合理的 Band-A Event 都必须获得最终编辑处置；若不入选，必须留下明确的 evidence-based rationale。

#### Band B — Strong Candidate

具有明确本周触发因素或执法/规则事件的持续性系统与竞技问题，例如匹配、反作弊、输入政策或重大技术故障。

#### Band C — Contextual Candidate

与命名的本周活动、赛事、版本或联动直接绑定，并具有独立客户价值的 Creator 内容、解释内容、信息或社区实用内容。

Creator 内容不得被一概降级；如果它与具体本周事件强绑定，可以进入正式候选。

#### Band D — Normally Demote

常规帮助、设置/新玩家问题、缺少本周触发的窄幅重复问题、周边内容/meta 讨论，或并非玩家直接讨论对象的抽象归纳。

`Trust`、`Friction`、`Uncertainty`、`Pressure`、泛化的 `Direction` 等分析结果通常应写入正文，而不是占用 Driver 标题与席位。

### 4.2 Selection Gates

每个 Driver Candidate 在最终入选前必须检查：

1. **Concrete Object / Event**：读者能明确知道玩家在讨论什么；
2. **Current-week Trigger**：持续性议题必须说明为什么属于本周；
3. **Client Relevance**：是否实质影响玩家体验、产品认知、购买/参与判断、赛事或社区理解；
4. **Evidence Breadth**：证据是否足以支持当前结论范围，不能把单一极端观点扩大为广泛 Driver；
5. **Band-A Coverage**：任何 C/D 候选占用最终席位前，所有合理 Band-A Event 均须已有明确处置；
6. **Context Integrity**：不能因为语义相似而替换不同主体或不同上下文，例如中国职业战队赛事表现不等于泛化 Creator Performance；
7. **Specificity**：不得把具体产品/事件泛化成会让读者误以为包含其他对象的上位类别；
8. **Operational Issue Restraint**：服务器、崩溃、接入和稳定性问题可以入选，但不能仅凭负面程度自动压过明确的版本、产品、玩法或赛事事件。

### 4.3 Event Coverage Gate

最终排序前，Event / Issue inventory 中的每一项都必须获得以下一种编辑处置：

- `Selected`
- `Merged`
- `Split`
- `Excluded`

要求：

- `Selected` 必须能追溯到承载该事件的最终 Driver；
- `Merged` 必须说明合并目标及合并理由；
- `Split` 必须说明拆分后的 Driver 及为什么需要独立结论；
- `Excluded` 必须说明为什么该事件不应占用本周正式 Driver 席位；
- Band-A Event 属于强制优先编辑复核对象；在其处置未明确前，不应先完成 C/D Candidate 的最终席位确认；
- 最终排序前，editorial synthesis 中不得存在 silently unresolved Event；
- 仅有宽泛语义关联或同属一个大类，不算 Event Coverage。

该 Gate 是编辑工作流约束，不替代 canonical `data_topic_editorial_review`。每个 current Data Topic 仍必须按 canonical business rules 保留其 disposition、rationale 与 provenance；同时不得因此把 canonical 中 `machine_hard_gate: false` 改成机器高影响力硬门槛，不得新增数值 high-impact 定义，也不得在未获单独批准时新增 machine-required schema 或 release blocker。

### 4.4 核心驱动因素与最终排序

在 Selection、Coverage、Granularity 与 Sentiment 审核完成后，再对最终入选 Driver 进行综合影响力排序。

前3个为核心驱动因素，其余为补充驱动因素。排序不设置固定的正向、中性、负向或 Mixed 组合，也不规定情绪标签先后顺序。

最终排序综合考虑：

- 讨论规模；
- 独立证据覆盖广度；
- 互动热度；
- 本周新增性或变化程度；
- 版本、赛事或业务重要性；
- 玩家体验影响；
- 是否具有跨周延续性；
- 证据可靠度与代表性。

**Evidence Qualification 只代表 Candidate 合格，不代表它应该进入正式周报。**

当不同指标结论不一致时，优先判断：**该 Driver 是否属于本周客户最需要知道的社区变化**。高互动不自动等于高影响力，单一高热帖子也不得仅凭互动量进入核心驱动因素。

### 4.5 话题数量规则

每周表单默认必须输出10个互不重复的 Driver：

1. 前3个为核心驱动因素，后7个为补充驱动因素，整体按综合影响力从高到低排列；
2. 情绪分布真实反映本周讨论，不得为了形成 Positive、Neutral、Negative 或 Mixed 的表面均衡而改变入选与排序；
3. 只有在完成 Event inventory、Selection Gates、Coverage、Granularity、代表性与重要性审核后，仍不足10个独立且足够重要的 Driver 时，才允许输出8或9个；
4. 不得通过重复标题、人工拆分同一事件、降低代表性标准、加入噪声或常规帮助内容来凑满10个；
5. 少于10个时必须保留 reduction audit；任何正式交付不得少于8个。

“合格的独立 Driver Candidate”至少必须满足：具体对象明确、真实 evidence 可追溯、原因可解释、与其他 Candidate 边界清楚，并通过 Selection、Coverage、Granularity、Sentiment 与代表性检查。

## 5. TOPIC / DRIVER 标题规则

### 5.1 标题功能

标题只负责概括**玩家本周实际讨论的具体对象、版本改动或事件**，不负责表达情绪，也不负责替分析师完成高阶归因。

### 5.2 标题要求

标题应：

- 优先使用2—5个英文单词；若保留必要的官方专名需要更长标题，以对象准确性优先，不得为了字数删除关键限定词；
- 使用名词或名词短语；
- 优先采用具体游戏对象、改动、系统、赛事、队伍表现或商业内容名称；
- 与社区实际讨论对象一致；
- 一个标题只对应一个有边界的玩家判断对象；
- 避免情绪化形容词。

### 5.3 Minimum Sufficient Specificity

标题必须保留“最小充分具体性”。如果删除某个产品、赛事、队伍或版本限定词后，读者会合理地误以为 evidence 覆盖了更多产品、皮肤、Creator、战队或事件，则该限定词不得删除。

例如：

- 使用 `Mythic Skippy Alternator`，不得泛化为 `Collaboration Reward Value`；
- 当 evidence 实际评价 C.A.R. Prestige Skin 时，不得仅写 `Cosmetic Questions`；
- 中国职业战队在命名赛事中的表现，不得替换为泛化的 `Creator Performance`。

同样不得过度缩窄。如果 evidence 和客户结论覆盖更宽的同一赛事/队伍表现，不应只截取某一场比赛作为最终标题。

### 5.4 抽象概念处理

除非社区本身反复、直接讨论该抽象概念，否则不应使用以下类型词语作为标题核心：

- Trust
- Friction
- Uncertainty
- Pressure
- Choices
- Direction
- Monetization Intent

这类分析结论如有充分证据，应放在正文中解释，而不是替代具体讨论对象成为标题。

### 5.5 推荐写法

- Bloodhound Rework
- Weapon Balance
- Energy Ammo Rework
- Looting System
- Heirloom Pack
- Mythic Skippy Alternator
- ALGS China Team Performance
- Anti-Cheat

### 5.6 不推荐写法

- Balance and Monetization Trust
- Collaboration Reward Value（当 evidence 只讨论 Mythic Skippy）
- Creator Performance Interest（当 evidence 实际讨论职业战队赛事表现）
- Season-Change Direction Draws Pushback
- Bad Solo Queue Experience
- Players Hate the New Skin

原因：标题应首先告诉客户“玩家在讨论什么”，并保持与 evidence 相同的对象边界；心理、信任、方向、购买意图等二次解释通常进入正文。

## 6. Sentiment 情绪判断规则

表单使用当前合同支持的四类标签：

- Positive
- Neutral
- Negative
- Mixed

不得把真实 Mixed 强制归入 Neutral。情绪标签必须来自对当周 evidence 的编辑复核，模型结果仅作为辅助证据，不得把模型多数直接当作最终投票结果。

### 6.0 前置条件：先固定 Driver Boundary

Sentiment 只能在 Step 4 Granularity 已经固定最终 Driver 对象后判断。

如果 Driver 从“大类”缩窄到某个负面子事件，或把多个不同事件合并在一起，情绪方向可能随之改变。因此 Granularity 发生变化后必须重新判断 Sentiment。

### 6.1 Dominant Sentiment + Minority Caveat

判断时优先观察：

- 同方向观点是否在多条独立 evidence 中重复出现；
- 是否跨不同内容来源或玩家出现；
- 主要反应是否明显强于少数相反意见；
- 少数意见是在否定核心价值判断，还是仅补充机制、价格、条件、使用疑问或 workaround；
- evidence breadth、recurrence、source scope 与 representativeness 是否支持当前结论。

当前规则不批准机器使用固定百分比阈值，因此不得自行创建“60%为 Positive”之类数值门槛。

### 6.2 Positive

当认可、满意、期待、支持、价值认同、参与/购买兴趣等正向评价清晰占主导时，判断为 Positive。

少数预算疑问、机制疑问、购买顾虑或负向 caveat 不会自动把 Positive 改成 Neutral 或 Mixed；只有当负向观点也达到实质代表性，且正向不再明显主导时，才进入 Mixed 判断。

正文应说明：玩家认可什么、为什么认可、可能影响什么，并保留有分析价值的少数负向 caveat。

### 6.3 Negative

当挫败、失望、不满、不信任、体验受损、非可用性、价值下降等负向评价清晰占主导时，判断为 Negative。

少数 workaround、替代方案或接受意见不会自动把 Negative 改成 Neutral 或 Mixed。

正文应说明：玩家不满意什么、具体原因、比较基准或结果影响，并保留有意义的少数正向 caveat。

### 6.4 Neutral

Neutral 用于以下情况：

- 讨论主要是机制、信息、规则、解释、验证、问题定义或事实描述；
- 当前 evidence 未形成稳定的正向或负向价值方向；
- 情绪并非讨论的核心内容。

Neutral **不是** Positive 与 Negative 相互抵消后的中点。仅仅同时出现正向和负向观点，不足以判定 Neutral。

### 6.5 Mixed

仅当以下条件同时成立时使用 Mixed：

1. Positive evidence 具有实质代表性且可追溯；
2. Negative evidence 具有实质代表性且可追溯；
3. 两个方向都属于同一个最终 Driver，而不是两个本应拆开的事件；
4. 两个方向都是该 Driver 的核心反应；
5. 综合 evidence breadth、recurrence、source scope 与 representativeness 后，没有一个方向明显占主导。

不得因为以下原因使用 Mixed：

- 只有一两条相反意见；
- evidence 不完整；
- 评论正文不可见；
- 事实尚未确认；
- 模型置信度低；
- 分析者不愿选择主导方向。

这些情况应调整 Evidence Confidence、限定措辞或进入人工复核，而不是把 Mixed 当成 uncertainty bucket。

### 6.6 Evidence Confidence 与 Sentiment 分离

Evidence Confidence 描述证据完整性与结论可靠程度；Sentiment 描述玩家评价方向。两者不得混为一体。

例如：

- 未确认的未来版本信息可以具有 Positive anticipation；“未确认”只影响 confidence，不自动变成 Neutral；
- 作弊行为本身是负面问题，但如果 Driver 的评价对象是“快速封禁/有效执法”，玩家对该响应可以形成 Positive；
- Dominant Positive + Minority Negative 应保留 Positive，并把 minority 写入 caveat；Dominant Negative 同理。

## 7. 单个话题的标准叙述结构

每个话题默认采用2—3句紧凑叙述，但硬长度必须以 active report contract 为准。当前 `1.2-narrative-length` 合同要求：每种语言至少1句话，英文正文20—75个英文单词。不得自行提高硬性最低句数/词数，也不得为了长度机械填充无关背景。

按照以下顺序书写：

> 玩家范围 + 评价对象 + 直接反应 + 具体原因 + 比较或转折 + 结果影响

并非每一条都必须出现全部六项，但至少必须包含：

1. 评价对象；
2. 玩家反应；
3. 一个具体原因；
4. 一个结果或判断。

## 8. 通用叙述公式

### 8.1 英文公式

```text
[Player scope] + [reaction verb] + [topic] + [clear evaluation].
[Evidence / cause / comparison], resulting in [experience, perception, anticipation, participation or purchase impact].
```

### 8.2 中文理解

> 【玩家范围】认为【话题对象】呈现出【明确评价】。讨论主要集中在【具体原因或证据】，并进一步影响了玩家的【体验、认知、期待、参与或购买行为】。

---

## 9. 正向话题叙述规则

### 9.1 核心结构

> 具体亮点 → 玩家认可 → 后续期待或参与

### 9.2 英文模板

```text
Players found [topic] highly engaging, particularly because of [specific highlight], building stronger anticipation for [future content or event].
```

### 9.3 中文规则

> 玩家认为【内容】具有【正向特征】，其中【具体亮点】获得较多认可，进一步提升了玩家对【后续内容、赛事或模式】的期待。

### 9.4 推荐动词

- praised
- welcomed
- enjoyed
- highlighted
- appreciated
- found engaging
- responded positively to
- showed interest in

### 9.5 结果表达

- building anticipation
- driving interest
- increasing participation
- reinforcing positive perception
- encouraging sharing
- supporting viewership growth

---

## 10. Neutral / Mixed 话题叙述规则

### 10.1 Neutral — 信息 / 机制讨论型

结构：

> 讨论对象 → 信息、机制或规则理解 → 当前无稳定价值方向

英文模板：

```text
Players discussed how [feature, policy or system] works and compared different interpretations. The discussion remained primarily informational, with no stable positive or negative evaluation established.
```

中文规则：

> 玩家主要围绕【功能、政策或系统】的运行方式与不同解释展开讨论。当前内容以信息理解或机制验证为主，尚未形成稳定的正向或负向评价。

### 10.2 Neutral — 原因 / 问题定义型

当玩家主要讨论“问题真正是什么”“哪个原因更重要”“官方说法是否准确”，且没有稳定价值方向时，可使用 Neutral。

英文模板：

```text
Players debated what was actually driving [issue], questioning whether [factor A] explained the problem. Attention instead centered on [factor B], without forming a stable positive or negative judgment about the broader topic.
```

### 10.3 Mixed — 实质双向对立型

Mixed 只用于两个方向都具有实质、可追溯 evidence 且没有明显主导方向的情况。

结构：

> 实质正向观点 → 实质负向观点 → 两边均为核心 → 无明显主导

英文模板：

```text
Players were materially divided on [topic]: one group valued [positive aspect], while another repeatedly criticized [negative aspect]. Both positions were central to the same discussion, and neither direction clearly dominated the reviewed evidence.
```

中文规则：

> 玩家对【话题】形成了实质性的双向评价：一部分玩家认可【正向因素】，另一部分玩家持续批评【负向因素】。两种立场都属于同一讨论核心，当前 evidence 无法确认明显主导方向。

如果一方明显主导，则必须改用 Positive 或 Negative，并把另一方写成 Minority Caveat。

---

## 11. 负向话题叙述规则

### 11.1 核心结构

> 问题 → 具体影响 → 玩家不满 → 行为或判断影响

### 11.2 英文模板

```text
Players criticized [change or issue] because [specific reason] directly affected [gameplay, fairness, access or value]. The repeated concern weakened confidence in [specific experience or decision], even though a smaller group described [minority workaround or acceptable aspect].
```

### 11.3 中文规则

> 玩家批评【改动或问题】，主要因为【具体原因】直接影响【体验、公平、接入或价值】。相关不满进一步削弱了玩家对【具体体验或判断】的信心，但少数玩家仍提到【次要 workaround / 可接受部分】。

---

## 12. 赛事内容规则

赛事类 Driver 必须保留赛事上下文与真正的评价主体。

优先明确：

- 哪个赛事；
- 哪支队伍或哪些职业选手；
- 玩家关注的是赛制解释、队伍表现、赛事结果还是内容剪辑；
- 该赛事内容带来的期待、观看或认知影响。

不得仅因为两个内容都涉及“performance”就互相替代。

例如：

- `ALGS China Team Performance` 表示中国职业队伍在赛事中的表现；
- `Creator Performance Interest` 表示社区 Creator 的个人操作、设备、设置或技巧内容；
- 两者属于不同主体与不同使用场景，不得合并。

---

## 13. 联动与 Cosmetic 内容规则

联动内容必须区分：

- 整体活动；
- 模式；
- 角色模型；
- 第一人称手模；
- 某个武器皮肤；
- 终极奖励；
- 整体奖励价值；
- 价格 / 获取机制。

如果 evidence 只评价其中一个具体对象，不能升级为整个联动体系判断。

例如：

`Mythic Skippy Alternator` 是具体终极奖励。若玩家讨论的是其外型、检视、特效、语音或还原度，标题与正文必须围绕 Skippy 本身；不得用 `Collaboration Reward Value` 代替，因为后者会误导读者认为 conclusion 同时覆盖整个联动中的其他皮肤与奖励。

---

## 14. 机制、英雄与武器平衡规则

### 14.1 Merge 同一 Event 的多个影响角度

如果多个 evidence cluster 都源于同一具体系统改动，并形成同一玩家结论，应优先合并。

例如：

- Loot Scarcity
- Combat Pace
- Supply / Recovery

如果都来自同一个 Loot System Overhaul，且共同指向资源不足、恢复困难与战斗节奏影响，则应作为一个 Driver，而不是占用多个席位。

### 14.2 Keep Separate 不同命名机制

如果是独立的具体改动，具有独立玩家反应或客户含义，应保持独立。

例如：

- Weapon Balance
- Energy Ammo Rework
- Corrupted Attachments

即使都属于 Gameplay / Weapons，也不能因为同属大类而合并。

### 14.3 Supporting Cause 不自动成为新 Driver

如果“商业化时间点”“信任担忧”“购买猜测”等只是对某个 Weapon Balance / Skin Event 的解释或 caveat，而没有形成独立讨论对象，应写入正文，不单独占用 Driver 席位。

---

## 15. 技术问题叙述规则

技术类 Driver 应明确：

- 具体故障；
- 发生环节；
- 对匹配、进入游戏、服务器、反作弊或运行稳定性的影响；
- 玩家是否有可重复观察的 workaround 或影响判断。

技术问题可以成为高重要性 Driver，但不得因为负面程度高就自动位于版本改动、产品或赛事之上。排序仍需与其他当周 Event 进行编辑重要性比较。

---

## 16. 购买与商业化规则

涉及购买判断时，区分：

- 对产品本身的评价；
- 价格 / 价值；
- 获取机制；
- 保底机制；
- 预算或购买疑问；
- 商业化时机担忧。

Dominant Sentiment 与 Minority Caveat 必须分开处理。

例如：

- 大量 evidence 明确认可 Heirloom Pack 的低成本价值，而少量玩家询问抽取预算或提醒风险 → `Positive`，预算问题写入 caveat；
- 大量玩家批评武器过度削弱，而少数玩家认为替代配置仍可使用 → `Negative`，替代意见写入 caveat；
- 只有当正负两边都具有实质代表性且无主导时才使用 `Mixed`。

---

## 17. 证据范围与玩家群体规则

### 17.1 玩家范围必须与 evidence 匹配

优先使用：

- 部分玩家；
- 赛事观众；
- 控制器玩家；
- 高段位玩家；
- 高消费玩家；
- 内容创作者；
- 一篇公开搜索可见帖子。

### 17.2 禁止无 evidence 扩大范围

不得把：

> some players

写成：

> the community

除非 evidence 覆盖与代表性足以支持。

### 17.3 一篇 Search-visible Post

如果只有一篇可公开搜索帖子支持 Driver，应明确这是有限 evidence，并说明评论正文缺失或细节尚未确认等限制。

该限制影响 confidence 与措辞强度，但不自动决定 Sentiment。

---

## 18. 结果影响与因果边界

### 18.1 可以写的影响

当 evidence 支持时，可写：

- 理解；
- 兴趣；
- 参与；
- 观看关注；
- 游戏连续性；
- 公平性判断；
- 购买兴趣；
- 对某个具体功能或体验的信任。

### 18.2 不得无 evidence 推断

不得直接推断：

- 销售一定下降；
- 大量玩家流失；
- 品牌信任完全崩塌；
- 活跃用户必然减少。

可使用谨慎表达：

- reduced interest in
- may weaken purchase intent
- appears to have discouraged participation
- contributed to lower enthusiasm

---

## 19. 补强的内部判断规则

以下规则用于提高 Driver 选择与叙述准确性，但不得改变表单结构，也不得创建未经批准的机器数值 Impact Score。

### 19.1 Event Inventory 与 Coverage

在最终排序前，必须完整列出当周可识别的 Current-week Event / Issue，并为每个 Event 留下 `Selected / Merged / Split / Excluded` 编辑处置。

- Band-A Event 未解决时，编辑流程应优先完成其处置，避免低优先级 Candidate 静默抢占最终席位；
- Partial semantic overlap 不算 coverage；
- umbrella Driver 若合并多个 Event，必须能够逐一追溯并说明 merge rationale；
- Event Coverage 不替代 canonical Data Topic disposition。

### 19.2 讨论规模与 Evidence Breadth

在确定 Driver Candidate 是否进入表单前，应检查：

- 帖子数量；
- 评论数量；
- 互动量；
- 是否由单一高热帖子主导；
- 是否跨多个独立内容来源出现；
- evidence 是否足以支持当前叙述范围。

### 19.3 事件重要性 / Selection 检查

除“有没有证据”外，还必须判断 Candidate 是否足以成为本周正式 Driver。

优先检查：

- 是否属于本周新增或明显变化的具体事件；
- 是否与版本核心改动、英雄、武器、玩法、商业内容或赛事直接相关；
- 是否影响玩家体验、理解、参与、观看或购买判断；
- 是否比常规帮助、窄幅重复问题或抽象分析结论更值得客户优先关注；
- 技术/接入问题是否真的比同周明确版本与产品事件具有更强的周度 materiality。

Evidence 完整但本周重要性较低的 Candidate 可以被 Excluded；不得因为“能够写成一条”就自动进入 Top Drivers。

### 19.4 Granularity 检查

自动化或人工必须检查：

- 两组 evidence 是否其实评价同一个具体 Event；
- 是否共享同一个 current-week trigger；
- 是否支持同一个玩家判断与 dominant conclusion；
- 次级内容是否只是 cause / caveat / impact；
- 合并是否会隐藏独立命名事件；
- 拆分是否只是重复同一事件的不同 impact angle；
- 标题是否过宽或过窄。

### 19.5 代表性检查

判断内容是否代表一个可识别的社区反应，而非个别意见。

建议内部区分：

- 高代表性：多个独立来源、方向一致；
- 中代表性：讨论量有限但方向清晰；
- 低代表性：单一来源或样本过少。

低代表性内容如必须写入，应使用：

- Some players...
- A smaller group of players...
- Discussion among [specific segment]...

### 19.6 Evidence Confidence 检查

Evidence Confidence 与 Sentiment 分开判断。

内部检查：

- Event / Issue 识别是否明确；
- Driver 是否与其他 Candidate 重复；
- evidence 是否完整、可追溯；
- 是否缺少评论正文或存在未确认信息；
- 原因是否来自真实文本；
- 结论是否超出样本。

Confidence 影响措辞强度与是否需要人工 review，但不得自动把 Sentiment 变成 Neutral 或 Mixed。

### 19.7 跨周变化检查

若话题延续自上周，应在正文中说明新变化，而不是重复旧结论。

可关注：

- 讨论升温或降温；
- 由期待转为实际评价；
- 由体验问题转为原因归因；
- 官方澄清后观点变化；
- 问题是否已解决。

跨周信息应融入现有正文，不新增可见字段。

## 20. 数据层补强规则

### 20.1 Weekly Conversations

该数据用于说明：

- 本周总体讨论规模；
- 样本基础；
- 社区是否出现明显升温或降温。

不得仅凭总讨论量判断情绪好坏。

### 20.2 Engagements

该数据用于说明：

- 内容传播强度；
- 玩家互动意愿；
- 话题是否形成高参与讨论。

高互动不等于正向情绪。

负向争议同样可能带来高互动。

### 20.3 数据与正文关系

正文不得机械引用总量数据，而应利用数据判断：

- 哪些话题值得进入表单；
- 哪些话题只是少量噪声；
- 哪些观点具有更高代表性。

## 21. 自动化生成规则

当模型自动填写该表单时，必须执行以下步骤。该流程属于 Weekly Driver 的编辑生成逻辑，不改变冻结 canonical Topic 注册表。

### 第一步：读取 Data Topic 与真实 evidence

保留 canonical Topic ID、来源与文本证据用于 provenance。Data Topic 不能直接作为最终 Weekly Driver。

### 第二步：建立 Current-week Event / Issue inventory

从当周 evidence 中识别全部可辨认的具体事件、对象、改动与问题，不先按最终 Driver 数量截断。

### 第三步：形成 Driver Candidate 并执行 Selection Ladder

每个 Candidate 必须具有明确对象、可追溯 evidence、至少一个具体原因，并分配 A / B / C / D Priority Band。

同时执行 Selection Gates：Concrete Object、Current-week Trigger、Client Relevance、Evidence Breadth、Context Integrity、Specificity 与 Operational Issue Restraint。

### 第四步：执行 Granularity Decision

判断哪些 evidence cluster 应 Merge、Keep Separate 或 Rename / Rebound。

- 相同对象 + 相同 trigger + 同一 coherent judgment 可合并；
- 不同命名事件、独立反应或独立客户含义必须保持独立；
- category overlap 不等于同一 Event；
- 抽象分析结论不得替代具体 discussion object。

### 第五步：完成 Event Coverage Gate

Event inventory 中每一项必须得到 `Selected / Merged / Split / Excluded` 处置并保留 rationale。

- Band A 未解决时应优先完成编辑处置，不应先确认 C/D Candidate 的最终席位；
- Final Ranking 前 editorial synthesis 不得存在 silently unresolved Event；
- Partial semantic overlap 不算 Event Coverage；
- 同时继续满足 canonical Data Topic disposition / provenance 规则。

### 第六步：识别玩家群体

根据 evidence 使用与样本强度相符的玩家范围，例如赛事观众、段位玩家、控制器玩家、高消费玩家、内容创作者或特定角色玩家。

### 第七步：判断 Sentiment

在最终 Driver Boundary 固定后，依次判断：

1. 是否主要为信息/机制/解释且无稳定价值方向 → Neutral；
2. 是否有清晰主导 Positive → Positive + 必要 minority caveat；
3. 是否有清晰主导 Negative → Negative + 必要 minority caveat；
4. Positive 与 Negative 是否都具有实质代表性、属于同一 Driver 且均无主导 → Mixed；
5. evidence 不完整、事实未确认或模型不确定 → 调整 confidence / review，不得自动使用 Neutral 或 Mixed。

### 第八步：提取原因、比较与结果影响

每条至少提取一个来自真实 evidence 的具体原因；存在比较时写明 benchmark；存在结果影响时，只写 evidence 支持的体验、认知、期待、参与、观看或购买影响。

不得在没有直接证据时把局部反馈升级为社区整体的信任、流失或商业化判断。

### 第九步：选择最终 Driver 并排序

1. 从已经完成 Selection、Coverage、Granularity 与 Sentiment 审核的 Candidate 中选择最终 Driver；
2. 默认输出10个，只有在确实不足10个独立且足够重要的 Driver 时才允许8或9个；
3. 综合讨论规模、独立 evidence breadth、互动、本周变化、版本/赛事/业务重要性、玩家体验影响与 evidence reliability 进行排序；
4. 前3个为核心驱动，其余为补充驱动；
5. 不得为了情绪标签均衡而改变入选与排序；
6. 不得用常规帮助、抽象 synthesis、重复拆分或噪声补足数量；
7. 当前没有批准的 numeric Impact Score，不得自行创建权重公式或硬阈值。

### 第十步：生成中英文 Narrative 并质检

- 硬性长度跟随 active report contract；当前 `1.2-narrative-length` 为每种语言至少1句话，English narrative 20—75个英文单词；
- 默认2—3句紧凑表达，但不得把偏好写成高于合同的 hard gate；
- 保持 Audience Scope → Evaluated Object → Direct Reaction → Specific Reason → Observed Impact；
- 删除重复信息、原始评论、无关背景、未经支持的推断和 pipeline / Topic assignment 语言；
- 检查标题具体性、Granularity、Sentiment、minority caveat、evidence boundary 与 bilingual meaning alignment；
- 最后运行 narrative validator 与 workbook contract validator，不得削弱 validator 让报告通过。

## 22. 强制质检清单

### 22.1 结构、Selection 与 Coverage 检查

- [ ] 保留现有表单结构，未新增或删除可见字段；
- [ ] Final Driver 不是从 canonical Data Topic 直接复制生成；
- [ ] 已建立完整 Current-week Event / Issue inventory；
- [ ] 每个 Event 均有 `Selected / Merged / Split / Excluded` 处置及 rationale；
- [ ] 无 Band-A Event 被低优先级 Candidate 静默挤出；
- [ ] Partial semantic overlap 未被当成 Event Coverage；
- [ ] 已执行 Selection Ladder 与 Selection Gates；
- [ ] Evidence-qualified 但重要性不足的 Candidate 没有自动入选；
- [ ] 默认共输出10个 Driver；不足10个时已完成 reduction audit，且不少于8个；
- [ ] 未通过重复、噪声、常规帮助内容或人工拆分凑数；
- [ ] 所有 current Data Topic 仍满足 canonical disposition / provenance 要求。

### 22.2 Granularity 与标题检查

- [ ] 一个 Driver 只对应一个有边界的玩家判断对象；
- [ ] 同一具体 Event 的不同 impact angle 未被无理由拆成多个 Driver；
- [ ] 不同命名 Event 未因同属一个 Data Topic / Category 被无理由合并；
- [ ] 标题保留最小充分具体性；
- [ ] 未用泛化的 Collaboration Reward、Creator Performance 等词替代更具体的 evidence 对象；
- [ ] 未把 Trust、Friction、Uncertainty、Pressure、Direction 等抽象推论无 evidence 地提升为标题；
- [ ] 标题未过度缩窄到不能覆盖同一 coherent Event 的重要 evidence。

### 22.3 Sentiment 检查

- [ ] Sentiment 在 Granularity 固定后判断；
- [ ] Positive 有清晰且主导的正向 evidence；
- [ ] Negative 有清晰且主导的负向 evidence；
- [ ] Neutral 只用于信息/机制/解释或无稳定价值方向，不是正负相抵后的中点；
- [ ] Mixed 仅用于正负两边都实质代表、同属一个 Driver 且无明显主导；
- [ ] 少数相反意见被作为 minority caveat 保留时，没有无故改变主流标签；
- [ ] evidence confidence 与 sentiment direction 已分开处理；
- [ ] speculative / unconfirmed 没有被自动判成 Neutral；
- [ ] 未把模型多数当作最终情绪投票。

### 22.4 叙述与长度检查

- [ ] 开头明确玩家范围与反应；
- [ ] 至少包含一个具体原因；
- [ ] 存在比较时写明比较对象；
- [ ] 存在行为影响时写明 evidence 支持的影响；
- [ ] 中英文句数与英文词数满足 active report contract；当前 `1.2-narrative-length` 为每种语言至少1句话、英文20—75词；
- [ ] 默认保持2—3句紧凑表达（非额外 hard gate），未为了字数机械填充；
- [ ] 未重复标题或标签；
- [ ] 未把局部意见推演为无 evidence 的社区整体信任、流失或商业意图。

### 22.5 代表性与置信度检查

- [ ] 少量观点使用范围限定；
- [ ] 特定玩家群体未被泛化；
- [ ] 单一高热帖子未被误写为社区共识；
- [ ] 结论强度与 evidence confidence 一致；
- [ ] 数据源边界和有限样本限制未被忽略。

### 22.6 语言检查

- [ ] 使用具体评价词；
- [ ] 使用因果、转折或比较逻辑；
- [ ] 未使用情绪化或绝对化表达；
- [ ] 未直接复制玩家原话；
- [ ] 未出现分析师个人判断口吻；
- [ ] 中英文 meaning alignment 一致。

## 23. 禁止使用的叙述方式

不得：

- 只写话题名称，不解释原因；
- 只重复 Positive、Neutral、Negative 或 Mixed；
- 将两个无关问题放入同一话题；
- 将少量玩家意见写成全体共识；
- 使用 everyone、all players 等绝对表达；
- 使用 good、bad 等模糊评价代替具体判断；
- 在无证据时断言销售、流失或收入变化；
- 用高互动量直接证明正向或负向情绪；
- 直接复制原始评论；
- 改变表单现有字段和排列结构。

---

## 24. 最终填写标准

一条合格的表单内容应同时满足：

> 看标题知道玩家本周在讨论什么具体对象或事件；  
> 看标签知道主导情绪方向，或在真正双向对立时知道其为 Mixed；  
> 看正文知道玩家为什么这样评价；  
> 看 caveat 知道是否存在有代表性的少数意见；  
> 看结尾知道该讨论可能影响什么。

Weekly Driver 的完整编辑链路应为：

> Raw Community Data → Data Topic → Current-week Event / Issue Inventory → Driver Candidate → Selection Ladder / Gates → Granularity Decision → Event Coverage Disposition → Sentiment Validation → Final Driver Selection → Editorial Importance Ranking → Bilingual Narrative

其中：

- Data Topic 用于稳定分类和 provenance，不等同于 Weekly Driver；
- Current-week Event / Issue 属于编辑归纳层，不新增 canonical Topic；
- Evidence Qualification 只决定 Candidate 是否合格，不等于最终入选；
- Event Coverage 要求每个 Event 有明确去向，但不替代 canonical Data Topic disposition；
- Granularity 先于 Sentiment，Driver Boundary 变化后必须重新判断情绪；
- Sentiment 支持 Positive / Neutral / Negative / Mixed，采用 Dominant Sentiment + Minority Caveat，Mixed 为高门槛状态；
- Evidence Confidence 与 Sentiment Direction 分开；
- 当前没有批准的机器数值 Impact Score 或 Sentiment 百分比阈值，不得自行创建；
- 每周默认输出10个 Driver，其中综合影响力最高的3个为核心驱动，其余为补充驱动；全部 Driver 按综合影响力排序，不设置固定情绪组合或顺序；
- 仅在完整 Selection / Coverage / Granularity 审核后仍不足10个独立且足够重要的 Driver 时允许8或9个，最低为8；
- 中英文长度满足 active report contract；当前 `1.2-narrative-length` 为每种语言至少1句话、English narrative 20—75词，并通过 `scripts/validate_narratives.py` 与 `scripts/validate_weekly_report_contract.py`。
