# 社区话题驱动因素表单叙述规则

> Rule version: `editorial-calibration-v1-2026-08-18`

## 1. 规则目的

本规则用于指导社区舆情分析人员或自动化模型，将一周内分散的玩家讨论整理为表单中的话题级摘要。

目标是让每一条内容清晰回答：

1. 玩家在讨论什么；
2. 玩家对该话题持什么态度；
3. 该态度由什么具体因素形成；
4. 该讨论是否影响体验、期待、信任、参与或消费行为。

---

## 2. 表单结构锁定原则

本规则不得改变现有表单结构。

从 W30 起，结构锁定为**单工作表左右中英对照**：英文位于左侧，中文位于右侧，同一驱动因素必须在同一行组中一一对应。不得输出中英文分离工作表，不得恢复为多页摘要、数据明细和质检分表。

现有结构保持为：

| 层级 | 当前字段 / 内容 | 功能 |
|---|---|---|
| 区域层 | CHINA | 界定分析市场 |
| 数据层 | Weekly Conversations | 说明本周社区讨论规模 |
| 数据层 | Engagements | 说明本周互动热度 |
| 话题层 | TOPIC / DRIVER | 概括社区讨论对象 |
| 判断层 | Positive / Neutral / Negative / Mixed | 标记话题情绪方向 |
| 解释层 | Narrative / Summary | 用2—3句紧凑文字解释玩家反应、原因与影响 |

不得新增、删除或调整表单中的现有字段。

允许补强的内容仅包括：

- 字段填写规则；
- 话题选择逻辑；
- 叙述顺序；
- 用词标准；
- 情绪判断标准；
- 数据质量检查；
- 自动化生成约束。

---

## 3. 表单整体写作逻辑

表单的核心叙述链路为：

> 话题对象 → 玩家反应 → 具体原因 → 比较或转折 → 结果影响

表单采用：

> 标签负责给出结论，正文负责解释结论。

因此正文不应机械重复 Positive、Neutral、Mixed 或 Negative，而应说明为什么形成该情绪判断。

---

## 4. 话题选择与排序规则

### 4.1 Current-week Event / Issue 先于 Driver 排名

在最终 Driver 排名前，先从 Data Topics 与证据中识别完整的 **Current-week Event / Issue inventory**。这里的 Event / Issue 是编辑综合层，不是新的 Topic 模型标签，也不得修改 frozen canonical topic registry。

每个 Event / Issue 必须在内部留下一个明确去向：

- `Selected`：作为独立 Weekly Driver 保留；
- `Merged`：并入另一个 Driver，并记录目标 Driver 与理由；
- `Split`：拆成多个独立 Driver，并记录子 Driver 与理由；
- `Excluded`：经过编辑复核后不进入最终报告，并记录具体排除理由。

不得因为某个 Event 已经被上位 Topic、宽泛 Driver 或相似类别覆盖，就默认认为它已经被 Weekly Driver 覆盖。

### 4.2 Editorial Selection Ladder

选择逻辑使用定性 A/B/C/D 编辑优先级，不设置数值 Impact Score。

#### A — Must Compete / 优先完成编辑复核

包括：

- 本周明确的新版本改动；
- Legend / Weapon Rework；
- 新机制、新模式、新系统；
- 明确命名的皮肤、Pack、Heirloom、联动终极奖励等产品对象；
- 商业化或经济机制；
- 重要赛事、资格赛、中国队伍表现等明确赛事事件。

例如：Bloodhound Rework、Looting System、Weapon Balance、Energy Ammo Rework、Corrupted Attachments、Heirloom Pack、Mythic Skippy Alternator、ALGS / ENC / EWC Team Performance。

A 类是**编辑复核优先级**，不是新增的机器 release hard gate。canonical business rules 中现有 machine hard-gate 口径保持不变。

#### B — Strong Candidate

包括具有明确本周触发因素、并对玩家体验或公平性造成实际影响的持续型问题，例如：

- D+ Solo Queue；
- Matchmaking；
- Anti-Cheat；
- Aim Assist；
- 明确的 Legend 使用问题；
- 严重 Server / Access / Reliability 问题。

#### C — Contextual Candidate

包括与明确本周事件绑定、具有独立客户价值的社区内容，例如：

- 赛事规则 Explainer；
- Event Information；
- 与联动 / 赛事直接绑定的 Creator Content；
- Creator Cosplay / Wildcard Preview。

Creator 内容不得因为“是 Creator 内容”而自动降级；关键在于它是否与具体本周事件绑定并形成独立社区价值。

#### D — Normally Demote

默认降低优先级的内容包括：

- Settings Help；
- New-player Help；
- 常规 Benchmark / Rank 问答；
- 常规队友寻找；
- 狭窄且重复出现的次级问题；
- peripheral highlight / meta content；
- `Trust`、`Friction`、`Direction` 等主要由机器抽象出来、并非玩家直接讨论对象的综合概念。

这类内容并非永远不能进入报告，但不得在更强的 A/B 类本周事件仍未完成复核时静默占用最终 Driver 席位。

### 4.3 第一层：核心驱动因素

优先呈现本周综合影响力最高的三个话题，并按综合影响力从高到低排列。

核心驱动因素不设置固定的正向、中性、Mixed 或负向组合，也不规定情绪标签的先后顺序。同一周的三个核心驱动可以出现相同情绪，具体分布必须由真实讨论证据和话题影响力决定，不得为了情绪平衡而调整排序或抬升代表性不足的话题。

核心驱动因素应综合考虑：

- 讨论规模；
- 互动热度；
- 业务影响；
- 玩家体验影响；
- 当前周的新变化或新触发；
- 赛事或版本重要性；
- 是否具有跨周延续性；
- 证据可靠性与覆盖范围。

当不同指标结论不一致时，应优先判断话题对玩家体验、业务决策和社区认知的实际影响，再结合讨论规模与互动热度确定最终顺序。高互动不自动等于高影响力，单一高热帖子也不得仅凭互动量进入核心驱动因素。

### 4.4 第二层：补充驱动因素

核心驱动因素之后，补充其他具有分析价值的话题，包括但不限于：

- 游戏体验；
- 新模式；
- 英雄平衡；
- 赛事讨论；
- 联动内容；
- 皮肤评价；
- 商业化机制；
- 反作弊；
- BUG与技术问题；
- 高价值玩家消费意愿。

补充话题继续按编辑重要性排序，而不是按正负情绪简单分组。

### 4.5 话题数量规则

每周表单默认必须输出10个互不重复的话题：

1. 前3个为核心驱动因素，按综合影响力从高到低排列，不设置固定情绪组合或情绪顺序；
2. 后7个为补充驱动因素，继续按综合影响力从高到低排列；
3. 情绪分布应真实反映本周讨论，不得为了形成正向、中性、Mixed、负向的表面均衡而改变话题入选结果或排序；
4. 只有当本周经过聚类、去重、事件覆盖和质量检查后，合格的独立话题不足10个时，才允许少于10个；
5. 话题不足时，应输出全部合格话题，并在生成记录中注明实际数量及不足原因；任何正式交付不得少于8个；
6. 不得通过拆分同一话题、重复相近标题、降低代表性标准或加入噪声内容来凑满10个。

## 5. TOPIC / DRIVER 标题与 Granularity 规则

### 5.1 标题功能

标题只负责概括玩家实际讨论对象，不负责表达情绪，也不应提前把机器推导出的体验、信任或商业影响当成讨论对象。

### 5.2 一个 Driver 的正确边界

一个 Weekly Driver 应对应一个有边界的玩家判断对象：

- 一个具体事件；
- 一个产品 / 皮肤 / Pack；
- 一个机制；
- 一个模式；
- 一次 Legend / Weapon 改动；
- 一次赛事 / 队伍表现；
- 一个清晰界定的问题。

该 Driver 应能够形成一条统一的：

> 玩家反应 → 原因 → 影响 / 结论

不同 Evidence angle 不自动意味着应拆成多个 Driver；同属一个 Topic / Category 也不意味着可以自动合并。

### 5.3 Merge 规则

多个 Evidence Cluster 满足以下条件时优先合并：

- 实际评价的是同一个具体 Event / Object；
- 共享同一个 Current-week Trigger；
- 形成同一个主要玩家判断；
- 形成同一个客户 takeaway；
- 其中一部分只是另一部分的 cause / caveat / reason / impact；
- 如果拆开，会造成同一事件重复占用多个 Driver 席位。

例如：

> Loot Scarcity + Supply / Recovery → Loot System Overhaul

当两组证据都在评价同一次 Loot System 改动时，不应仅因为影响维度不同就拆成两个 Weekly Driver。

### 5.4 Split / Keep Separate 规则

满足以下任一条件时应拆开或保持独立：

- 具体命名对象不同，即使属于同一 Data Topic；
- 一个命名 Rework / Product / Mechanic 有独立的玩家反应与结论；
- 玩家行为或客户影响不同，合并后会模糊结论；
- 合并会扩大证据实际覆盖范围；
- 上位 Driver 会吞掉一个具有独立客户意义的具体事件。

例如：

> ALGS China Team Performance ≠ ALGS Highlight Selection

> Bloodhound Rework 不应在存在独立玩家反应时被 Season 30 Legend Preview 静默吞掉。

### 5.5 Minimum Sufficient Specificity

标题必须保留“让读者正确识别讨论对象所需的最小充分限定词”。

判断方法：

> 删除某个限定词后，报告阅读者是否会合理地认为证据还包括其他产品、皮肤、赛事、Creator、队伍或事件？

如果会，则该限定词不能删除。

例如：

- 推荐：`Mythic Skippy Alternator`
- 不推荐：`Collaboration Reward Value`

当玩家实际讨论的是 Skippy 的外型、检视、特效和还原度时，后者会错误地扩张到整个联动奖励体系。

同样，标题也不得过度缩窄：如果本周证据和最终 takeaway 实际覆盖更完整的赛事 / 队伍表现，就不能只截取其中某一场比赛来替代完整事件边界。

### 5.6 抽象结论放在 Narrative

除非玩家本身就直接、反复讨论抽象概念，否则以下内容应优先放入正文：

- Trust；
- Friction；
- Pressure；
- Uncertainty；
- Direction；
- Purchase Intent；
- Monetization Concern。

标题优先说明：

> 玩家在讨论什么

正文再解释：

> 为什么重要、造成什么体验 / 信任 / 购买 / 参与影响

## 6. Sentiment 情绪判断规则

表单正式使用四类标签：

- Positive
- Neutral
- Mixed
- Negative

不得使用其他标签；四类标签必须依据可追溯的真实证据判断。

Sentiment 必须在最终 Driver Boundary 经 Granularity 复核后判断。Driver 边界变化后，Sentiment 必须重新评估。

---

### 6.1 Positive

当最终 Driver 范围内的证据明显以以下方向为主时判断为 Positive：

- 玩家认可内容质量；
- 玩家欢迎或支持变化；
- 玩家主动分享、推荐或参与；
- 玩家对后续内容形成积极期待；
- 玩家认可产品或商业价值；
- 赛事或活动提升正向关注；
- 讨论主要由积极体验驱动。

若存在少量或次要负向意见，应作为正文中的 Minority Caveat，而不是自动将标签改为 Mixed 或 Neutral。

---

### 6.2 Negative

当最终 Driver 范围内的证据明显以以下方向为主时判断为 Negative：

- 玩家体验明显受损；
- 内容低于预期；
- 公平性或信任受影响；
- 玩家频繁与更优内容进行负面对比；
- 购买、参与或使用意愿下降；
- 问题引发持续投诉；
- 讨论主要由失望、挫败或不满驱动。

若存在少量 workaround、适应方案或正向意见，应作为正文中的 Minority Caveat，而不是自动将标签改为 Mixed 或 Neutral。

---

### 6.3 Neutral

Neutral 仅用于：

- 机制理解；
- 信息讨论；
- 规则解释；
- 问题定义；
- 分析 / 验证；
- 事实性问题；
- 或其他没有形成稳定正负价值方向的讨论。

Neutral **不是** Positive 与 Negative 相互抵消后的中间标签。

不得因正向和负向意见同时存在就默认使用 Neutral。

---

### 6.4 Mixed

Mixed 仅用于：

- Positive 和 Negative 都有实质性、可追溯证据；
- 两种方向都属于同一个最终 Driver；
- 两种方向都是理解该 Driver 的核心反应；
- 在证据覆盖、重复出现、来源范围和代表性上，没有一个方向明显占主导。

以下情况不得使用 Mixed：

- 仅存在少量反向意见；
- 只是出现一个反例；
- Comment Body 缺失；
- 内容尚未证实；
- Evidence Confidence 较低；
- 模型不确定；
- 分析者不愿意选择主导方向；
- 实际上是两个应该在 Granularity 阶段拆开的独立事件。

Mixed 必须同时有实质性 Positive 与 Negative Evidence，且无明显 Dominant Direction。不得设置固定百分比或其他未经批准的数值阈值。

---

### 6.5 Evidence Confidence ≠ Sentiment

证据置信度与情绪方向必须分开处理。

例如：

- 一篇 Search-visible Post 评论正文不可见；
- Datamined 内容尚未确认；
- Evidence Coverage 较窄；

这些情况可以：

- 降低 Evidence Confidence；
- 在正文使用边界化语言；
- 进入 Editorial Review；

但不得仅因此自动判为 Neutral 或 Mixed。

---

### 6.6 Future-oriented / Speculative Discussion

“尚未发生”或“存在猜测”只描述信息确定性，不代表情绪方向。

如果玩家对未来内容表现出：

- 支持；
- 兴奋；
- 正向期待；

可以判断为 Positive。

如果玩家对未来内容表现出：

- 担忧；
- 反对；
- 明显悲观预期；

可以判断为 Negative。

---

### 6.7 Sentiment 必须绑定实际 Judgment Object

情绪必须判断玩家对当前 Driver 实际评价对象的态度，而不是仅判断该事件背景本身“好或坏”。

例如：

> Cheating 本身是负面问题。

但如果本周 Driver 实际评价的是：

> Anti-Cheat enforcement / prompt ban response

那么玩家对有效执法结果的反应可能是 Positive。

---

## 7. Minority Caveat 规则

当一个方向明显主导，但存在有意义的少数意见时：

### Dominant Positive + Negative Minority

标签：

> Positive

正文：

> 先说明主要赞扬 / 支持 / 价值认可，再补充少数预算、机制、质量或其他担忧。

### Dominant Negative + Positive Minority

标签：

> Negative

正文：

> 先说明主要挫败 / 批评，再补充少数 workaround、替代方案或支持意见。

少数意见不应因为存在就获得与主导方向同等权重。

---

## 8. 单个话题的标准叙述结构

中文与英文 Narrative 均至少使用 **2 个完整句子**。默认保持 **2—3 个紧凑句子**。

按照以下顺序书写：

> 玩家范围 + 评价对象 + 直接反应 + 具体原因 + 比较或转折 + 结果影响

并非每一条都必须机械出现全部六项，但至少必须包含：

1. 评价对象；
2. 玩家反应；
3. 一个具体原因；
4. 一个结果或判断。

英文正文不得少于 **25 words**。如果 active validator / contract 定义了更严格的最大长度或其他限制，以实际 validator / contract 为准；不得为了满足长度机械填充。

## 9. 通用叙述公式

### 9.1 英文公式

```text
[Player scope] + [reaction verb] + [topic] + [clear evaluation].
[Evidence / cause / comparison] explains the reaction, affecting [experience, perception, anticipation, participation, purchase, trust or the ability to form a judgment].
```

### 9.2 中文理解

> 【玩家范围】认为【话题对象】呈现出【明确评价】。讨论主要集中在【具体原因或证据】，并进一步影响了玩家的【体验、认知、期待、参与、购买或判断】。

---

## 10. 正向话题叙述规则

### 10.1 核心结构

> 具体亮点 → 玩家认可 → 后续期待 / 参与 / 价值判断

### 10.2 英文模板

```text
Players welcomed [topic] because [specific highlight] delivered clear value or a better experience. The response increased interest in [future content, participation or purchase], although [minority concern] remained for a smaller group.
```

### 10.3 中文规则

> 玩家认可【内容】带来的【具体价值或体验提升】。该反应进一步提升了对【后续内容、参与或购买】的兴趣，但少部分玩家仍对【次要担忧】保持谨慎。

---

## 11. 负向话题叙述规则

### 11.1 核心结构

> 体验 / 价值受损 → 具体原因 → 行为 / 认知影响 + 少数 Caveat

### 11.2 英文模板

```text
Players criticized [topic] because [specific change or limitation] made the experience less effective or less satisfying. The concern weakened [confidence, usage or purchase interest], although a smaller group found [workaround or acceptable aspect].
```

### 11.3 中文规则

> 玩家批评【内容】中的【具体改动或限制】，认为其削弱了实际体验或价值。相关担忧进一步影响了【信任、使用或购买意愿】，但少量玩家仍认可【替代方案或可接受部分】。

---

## 12. Neutral 话题叙述规则

Neutral 不是正负抵消。

### 12.1 原因 / 机制讨论型

英文模板：

```text
Players discussed how [issue or system] works and compared different explanations for the observed behavior. The exchange helped clarify the mechanism, but it did not establish a stable positive or negative judgment.
```

中文规则：

> 玩家围绕【问题或机制】比较不同解释，并尝试确认实际运行方式。相关讨论帮助社区理解【机制 / 原因】，但尚未形成稳定的正向或负向价值判断。

### 12.2 信息 / 规则理解型

英文模板：

```text
Discussion focused on [event, rule or feature] and the conditions surrounding it. Players used the available information to clarify [participation, acquisition or system details], without forming a clear evaluative direction.
```

中文规则：

> 讨论主要集中在【事件、规则或功能】及其具体条件上。玩家利用现有信息确认【参与、获取或系统细节】，但没有形成明确价值方向。

---

## 13. Mixed 话题叙述规则

Mixed 必须通过高门槛判断。

### 13.1 核心结构

> 实质 Positive → 转折 → 实质 Negative → 无主导方向

### 13.2 英文模板

```text
Players praised [positive aspect] and described concrete benefits for [experience or value]. Other representative reactions criticized [negative aspect] and reported a different impact, leaving neither direction clearly dominant across the reviewed evidence.
```

### 13.3 中文规则

> 一部分玩家明确认可【正向内容】及其带来的【具体收益】。另一部分具有代表性的证据则集中批评【负向内容】并描述不同影响，两种方向均有实质支持，且没有一方明显占主导。

如果无法明确写出两边的实质证据和“为什么没有主导方向”，不得使用 Mixed。

---

## 14. 赛事话题叙述规则

赛事类首先区分讨论对象：

- 赛事规则 / 赛制；
- 赛事结果；
- 中国职业队伍表现；
- 某支队伍 / 选手表现；
- 赛事 highlight / 内容选择；
- Creator 个人操作表现。

这些对象不得仅因为都属于 Esports 或 Performance 而互相替代。

例如：

> ALGS China Team Performance

不得用：

> Creator Performance Interest

替代。

赛事标题应保留识别讨论对象所需的赛事、队伍或上下文限定词。

---

## 15. 商业化与皮肤话题叙述规则

商业化内容必须区分：

- 某个明确 Cosmetic / Skin / Pack / Heirloom 的品质评价；
- 获取机制；
- 价格 / Value；
- 整个 Event Reward System；
- Purchase Intent。

具体产品评价不能无依据扩大成整个联动或奖励体系评价。

例如：

> Mythic Skippy Alternator

玩家讨论外型、检视、特效时，不能自动改成：

> Collaboration Reward Value

如果讨论主要认可低成本获得 Universal Heirloom，而少量玩家询问预算或机制：

> 应优先判断 Dominant Positive，并把预算 / 抽取担忧作为 Minority Caveat；不得仅因为存在负面问题就自动使用 Mixed。

---

## 16. 技术问题与 BUG 叙述规则

技术类可进入 Driver，但需要明确：

- 是否具有具体 Current-week Trigger；
- 是否影响 Match Entry / Play Continuity；
- 是否具有足够证据覆盖；
- 是否真的比同周核心版本 / 产品 / 赛事事件更重要。

Server / Crash / Access / Anti-Cheat Error 不得因为“负面程度强”就自动获得最高排序。

技术类正文应说明：

> 问题 → 具体影响 → 玩家处理 / 判断

而不是直接升级为：

> Community Trust Crisis

除非存在重复、直接、足以支持“Trust”本身成为讨论对象的证据。

---

## 17. 强度控制规则

### 17.1 高强度词

- widely praised
- strongly criticized
- broad backlash
- widespread concern
- dominant reaction

只能在证据覆盖足以支持时使用。

### 17.2 中强度词

- many players
- players generally
- several viewers
- a visible part of the discussion

需要与证据范围匹配。

### 17.3 低强度 / 边界化表达

- some players
- a smaller group
- several comments
- one search-visible post
- limited available discussion

当 Evidence Confidence 较低时，应降低主语强度，而不是自动把 Sentiment 改成 Neutral 或 Mixed。

---

## 18. 因果表达规则

仅当证据直接支持因果关系时使用：

- caused
- led to
- resulted in

否则优先：

- coincided with
- was associated with
- players linked it to
- discussion connected the issue with

机器不得把相关性自动写成因果关系。

---

## 19. 自动化生成流程

自动化系统建议按照以下顺序生成：

1. 读取数据质量结果；
2. 读取 Data Topics 与 Evidence；
3. 枚举 Current-week Event / Issue inventory；
4. 为每个 Event / Issue 记录证据与 Current-week Trigger；
5. 使用 A/B/C/D Selection Ladder 完成优先级复核；
6. 为每个 Event / Issue 留下 `Selected / Merged / Split / Excluded` 去向；
7. 在 Granularity 层完成 Merge / Keep Separate / Rename / Rebound；
8. 检查具体 Event 是否被上位 Topic / 抽象 Driver 静默吞掉；
9. 在最终 Driver Boundary 上判断 Sentiment；
10. 确定 Dominant Sentiment；
11. 记录有意义的 Minority Caveat；
12. 仅在无 Dominant Direction 且正负均有实质证据时使用 Mixed；
13. 最终排序并选出 8—10 个 Driver；
14. 先写中文，再写英文；
15. 检查中英文意义一致；
16. 检查每种语言至少2句、英文至少25词；
17. 检查是否存在过强措辞、过度推断、抽象标题、可疑 Merge / Split；
18. 运行现有 Narrative Validator 与 Workbook Contract Validator；
19. Validator 失败时修正文案或规则执行结果，不得弱化 Validator。

## 20. 自动质检清单

### 数据层

- [ ] 数据是否已通过质量门槛；
- [ ] 是否保留平台单位差异；
- [ ] 是否存在来源集中问题；
- [ ] 是否存在低样本限制。

### Selection / Coverage

- [ ] 是否完整枚举 Current-week Event / Issue；
- [ ] A 类事件是否优先完成编辑复核；
- [ ] 每个 Event 是否有 Selected / Merged / Split / Excluded 去向；
- [ ] 是否存在 Settings Help / New-player Help 等低优先内容挤掉具体本周事件；
- [ ] 是否存在技术问题因负面强度而自动过度排序；
- [ ] 是否存在语义类似但主体不同的错误映射。

### Granularity / Title

- [ ] 是否一个 Driver 对应一个清晰 Judgment Object；
- [ ] 是否存在同一 Event 被过度拆成多个 Driver；
- [ ] 是否存在多个独立 Event 被上位标题吞掉；
- [ ] 是否保留具体产品 / 赛事 / 队伍所需限定词；
- [ ] 抽象 Trust / Friction / Direction 是否被错误放进标题。

### Sentiment

- [ ] Sentiment 是否在 Granularity 确定后判断；
- [ ] 是否先判断 Dominant Direction；
- [ ] Positive / Negative 是否因少量反向意见被错误降为 Mixed；
- [ ] Neutral 是否被错误当成正负抵消；
- [ ] Mixed 是否同时存在实质 Positive 与 Negative Evidence；
- [ ] Mixed 是否确实没有 Dominant Direction；
- [ ] Evidence Confidence 是否与 Sentiment 分开处理；
- [ ] Speculative / Unconfirmed 是否被错误自动判为 Neutral；
- [ ] Sentiment 是否绑定真正的 Judgment Object。

### Narrative

- [ ] 中文是否至少2句；
- [ ] 英文是否至少2句；
- [ ] 英文是否至少25 words；
- [ ] 是否避免机械填充；
- [ ] 中英文是否同义；
- [ ] 是否说明具体原因；
- [ ] 是否说明影响 / 判断；
- [ ] 是否保留必要 Minority Caveat；
- [ ] 是否出现模板化流水线语言。

## 21. 最终目标

该表单不是为了复述评论，而是为了回答：

> **本周玩家围绕哪些具体事件形成了最重要的讨论，这些事件分别产生了什么主导反应，为什么，以及它们如何影响玩家体验、认知、期待、参与或购买判断。**

最终输出必须做到：

- Event 不静默丢失；
- Driver 具体；
- Selection 有编辑优先级；
- Granularity 合理；
- Sentiment 有主导方向依据；
- Mixed 不成为保守兜底；
- Minority Caveat 不篡改主导标签；
- 数据证据与表述强度匹配；
- 中英文一致；
- 保持现有表单结构。
